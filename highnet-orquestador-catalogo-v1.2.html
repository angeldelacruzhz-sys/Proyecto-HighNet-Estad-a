1. Contexto, objetivo y alcance integrado

HighNet es una empresa de reventas de tecnología que actualmente publica en su sitio web el catálogo del mayorista Syscom. Se incorpora un segundo mayorista, CT Internacional (CTOnline.mx), mediante su API CT-Connect. Esta versión 1.2 consolida en un solo diseño técnico la propuesta original del sitio y el ajuste posterior que introdujo comercialización configurable y panel administrativo.

1.1 Qué problema se resuelve

El objetivo no es simplemente sumar un segundo catálogo, sino construir una capa que permita comparar el mismo producto entre proveedores, elegir la mejor fuente por precio y calidad, y publicar en el sitio de HighNet un catálogo coherente que no dependa del dialecto ni de las reglas de negocio de cada mayorista.

El flujo comercial real que gobierna esta versión es:

cliente pide en hnet.com.mx -> HighNet recibe pedido/cotización -> HighNet compra al mayorista -> HighNet envía

La v1.0 añadió una meta que sigue siendo válida y se conserva aquí como horizonte funcional: igualar las funciones relevantes del cotizador de Syscom (“Cotice a su Cliente”), incluyendo catálogo de marca blanca, mezcla de productos propios y de proveedor, subcuentas con márgenes independientes, e IVA/margen por categoría. La v1.1 cerró primero la parte indispensable para vender en el sitio público: precio público controlado por HighNet y administración de márgenes desde backend.

1.2 Objetivo integrado v1.2

  • Una sola API interna consumida por el frontend público y por el panel admin.
  • Catálogo maestro unificado con dedupe, scoring de calidad y conservación de sources[].
  • Precio público calculado por backend con porcentaje configurable, IVA, tipo de cambio y redondeo.
  • Separación estricta entre lo que ve el visitante (precio final) y lo que ve el admin (costos, fuente, reglas, preview).
  • Base de datos preparada tanto para el flujo actual de pedido web como para el cotizador interno/white-label documentado desde la v1.0.

1.4 Principio arquitectónico central

El frontend de HighNet nunca consume las APIs de los proveedores directamente. Existe una sola API interna que consulta Syscom y CT, normaliza, fusiona, aplica reglas comerciales y devuelve contratos diferenciados para público y admin.

  • Agregar un tercer proveedor no requiere tocar el frontend; solo se agrega un adaptador y mapeos.
  • Las reglas de margen, IVA, tipo de cambio, calidad y selección viven en backend/base de datos, no duplicadas en pantallas.
  • Si un proveedor falla, el backend degrada la respuesta de forma controlada en lugar de romper el sitio.

3. Flujo de consulta de catálogo y precio de venta

Frontend -> GET /api/products -> Orquestador -> lee precios_publicados / caché -> refresco puntual cuando aplica Adaptadores Syscom + CT -> normalizador -> merge -> motor comercial

EscenarioFuenteRazón

3.1 Cadena de cálculo

  1. Los adaptadores traen costo original, moneda, stock y frescura. CT puede requerir conversión por tipo de cambio.
  2. El normalizador deja sources[] con costos comparables en MXN y stock operativo (CT = PUE).
  3. Para el catálogo público, se toma como costo de referencia la fuente con existencia y menor costo MXN.
  4. Se aplica la cascada de margen, luego IVA, luego la política de redondeo.
  5. Se escribe precios_publicados.precio_venta; eso es lo único que pinta el frontend público.

Fórmula base: precio_venta = redondear(costo_mxn_elegido × (1 + margen) × (1 + iva)).

Migración inicial sugerida desde el INCREMENTO = 1.25 actual: dejar margen_general = 0.25 e iva_default = 0.00 para no mover precios el día del corte, o desglosar después con una combinación equivalente.

5. Pipeline interno del normalizador

1. Mapeo al contrato -> 2. Limpieza correctiva -> 3. Validación bloqueante -> 4. Scoring de completitud -> 5. Dedupe y merge -> 6. Motor comercial -> 7. Salida

Figura 4 — El pipeline acumula marcas de calidad y sigue; solo las reglas bloqueantes detienen el producto.

#EtapaSalida
1Mapeo al contratoCampos HighNet por fuente; raw íntegro.
2Limpieza correctivaTítulo, stock negativo -> 0, marca canónica, precio texto -> decimal, TC a MXN.
3Validación bloqueanteSKU, precio > 0, moneda, título >= 3; stock CT operativo = PUE.
4Scoring de completitudFicha 0–100 por fuente (imagen, descripción, specs, etc.).
5Dedupe y mergeUPC / marca+modelo. Conserva sources[]; no colapsa a un precio.
6Motor comercialElige costo de referencia, aplica %, escribe precio_venta.
7SalidaContrato público (venta) y contrato admin (costos + preview).

Principio operativo: un registro con varias advertencias se publica; uno con una sola regla bloqueante no. Ese comportamiento ya estaba en la v1.0 y se preserva en la v1.2 porque es fundamental para distinguir entre degradar y ocultar.

6.3 Trazabilidad del pedido

El SKU canónico (MERCUSYS-MR70X) identifica el producto de catálogo. El código con el que HighNet compra al mayorista es sources[].providerId. Las líneas de pedido y cotización guardan ambos para evitar pérdida de rastreo operativo.

La v1.0 documentó de forma explícita que fieldsContributed explica por qué un producto muestra cierta imagen, descripción o categoría sin tener que abrir raw. Esa trazabilidad se mantiene en v1.2 porque es útil para soporte, QA y auditoría comercial.

11. Comercialización: porcentajes, IVA, tipo de cambio y panel admin

11.1 Libertad del administrador

El admin no captura el precio de góndola peso a peso. Configura porcentajes y el sistema calcula el precio de venta.

NivelCuándo aplicaEjemplo
ProductoExiste fila activa en reglas_margen_producto para ese SKU.Este UPS se vende con 18 % aunque Energía tenga 22 %.
CategoríaNo hay override de SKU; se usa reglas_margen_categoria.Networking > Routers = 28 %.
GeneralNo hay regla más específica.configuracion_comercial.margen_general = 25 %.

11.2 IVA y redondeo

iva_default vive en configuración (recomendado a futuro: 0.16). Una categoría puede tener iva_porcentaje propio. El catálogo público puede mostrar precio con IVA incluido; el pedido interno y el cotizador podrán desglosarlo. El redondeo por defecto es a 2 decimales, con opción a peso entero hacia arriba.

11.3 Tipo de cambio

  • Cada fuente guarda precio original, moneda y TC aplicado. Nunca se mezcla el TC de un proveedor con el costo del otro.
  • Modo automático: el job toma el TC documentado por CT para líneas CT; Syscom se trata como MXN salvo evidencia contraria.
  • Modo manual: el admin fija un valor vigente. Debe quedar auditoría (quién, cuándo, valor anterior).
  • Un TC erróneo puede subcotizar servidores; el panel debe mostrar origen, fecha y valor.

11.4 Interfaz de administración

El sitio permanece público. El login vive en un acceso discreto; si rol = admin y activo = true, el menú global muestra Administración -> /admin. El panel 3.0 existente (banners, cotizaciones web, pedidos, usuarios) se conserva y se amplía con:

13. Motor de selección de proveedor y score de calidad

El catálogo público de esta versión usa una regla simple: menor costo MXN con existencia (CT = PUE). El score de calidad del proveedor permanece documentado para la fase posterior y para no cerrar en falso el diseño de datos ya incorporado desde la v1.0.

13.1 Fórmula futura

score_fuente = (peso_precio × score_precio_normalizado) + (peso_calidad × score_calidad_proveedor)

  • Los pesos son configurables por categoría: un cable se decide casi solo por precio; un servidor o UPS pondera mucho más la calidad/garantía.
  • Las fuentes sin existencia se descartan antes del cálculo.
  • Empate dentro del umbral -> decisión humana con explicación.

13.2 Modos

ModoUso
AutomáticoElige sin preguntar cuando haya historial suficiente.
SugeridoPreselecciona y muestra alternativas. Modo inicial recomendado.
ManualSolo tabla comparativa. Útil para productos críticos o de alto valor.

13.3 Componentes del score

ComponentePeso inicialFuente del dato
Cumplimiento de entrega30 %Fecha prometida vs. fecha real de pedidos históricos.
Tasa de incidencias30 %Garantías, devoluciones y daños.
Garantía ofrecida20 %Meses de garantía del catálogo, normalizados.
Evaluación manual20 %Nota del equipo de compras.

Niveles: proveedor+marca, luego proveedor+categoría, luego proveedor general. Decaimiento temporal sugerido: ~6 meses. Arranque en frío: menos de 10 entregas -> solo evaluación manual, marcado preliminar.

14. Flujo de pedido en sitio y cotización

14.1 Pedido del sitio (flujo actual)

PasoDetalle
1. CatálogoEl cliente ve precio_venta. No ve costo ni mayorista.
2. CarritoLíneas con precio de venta vigente.
3. ConfirmaciónConsulta viva de costo. Si el delta con lo mostrado supera el umbral, se avisa o se bloquea; nunca se cambia el total en silencio.
4. CongeladoCada order_item guarda costo, TC, margen, IVA, id_fuente y sku_proveedor.
5. HighNet compraSe generan pedidos_proveedor agrupados. Syscom = manual; CT = API en fase posterior.
6. EnvíoHighNet cumple al cliente y el order público refleja estatus.

14.2 Cotizador interno / marca blanca (contenido reintegrado de la v1.0)

La v1.1 lo redujo a “fase posterior”; la v1.2 conserva el detalle funcional de la propuesta original para que no se pierda el objetivo de negocio.

PasoEtapaDetalle
1InicioEl vendedor selecciona o crea cliente y subcuenta; eso determina reglas de margen.
2BúsquedaSiempre sobre el catálogo maestro unificado, nunca por proveedor.
3Resolución de fuentesSe traen las fuentes con existencia y se calcula o muestra su score comparativo.
4PresentaciónModo automático/sugerido/manual según categoría o cliente.
5Margen e IVAOrden: margen de cliente o subcuenta, luego categoría, luego IVA. Puede existir ajuste manual auditado.
6Más líneasPueden convivir distintos proveedores y productos propios.
7RevisiónTotales, IVA, tiempo de entrega más lento, alertas por sobre pedido o score preliminar.
8DocumentoPDF con marca de HighNet, sin rastro del mayorista de origen.
9SeguimientoEstatus: enviada, vista, aceptada, vencida.
10Conversión a pedidoÓrdenes de compra agrupadas por proveedor. Si cambió el costo, el sistema avisa antes de confirmar.

Congelado de precios: cada línea guarda una copia del costo, el tipo de cambio y el margen usados al cotizar. No se referencia el catálogo en vivo al convertir a pedido.

18. Decisiones tomadas y riesgos abiertos

18.1 Decisiones firmes

  • El frontend público consume una sola API interna y un solo precio de venta.
  • El catálogo nunca expone al cliente el mayorista ni el costo.
  • El admin elige porcentajes (general / categoría / producto); el motor calcula el precio final.
  • El login no bloquea el sitio; el menú Administración depende del rol admin.
  • Stock CT de venta = Puebla.
  • Pedidos a Syscom: manuales. Pedido del sitio: HighNet compra y envía.
  • Precios públicos salen de precios_publicados; al confirmar se consulta costo en vivo.
  • El normalizador no elige proveedor ni aplica %; conserva sources[].
  • Ante duda en dedupe, no fusionar.
  • Se conserva y extiende el esquema 3.0 de users, orders, quotes, banners, coupons y addresses.
  • raw y sources no viajan en GET públicos.
  • Las cotizaciones internas congelan precio, tipo de cambio y margen en el momento de cotizar.

RiesgoMitigación
